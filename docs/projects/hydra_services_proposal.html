Service Containers

Any code can be a service. The container makes it one — a self-describing package authored by the network's Hermes, installed like a ComfyUI custom node, and improved every time it fails.

① Any code is a serviceCLI, API, batch, stream — if it runs and produces output, it can be wrapped.
② The Hermes authors itThe agent attached to the network writes the container as part of every install.
③ Failure improves itEvery failed run feeds back; the agent patches, versions, and re-serves.
The gap

Today vs. what's needed

Today a service is a row in a registry: a name, a command, some needs, reported by a client. That was enough to prove the loop (Human → Agent → GPU Worker → Verified Result). But it is a pointer to code, not a description of code. Nothing says how to install it, what it needs, which fields exist, or how to fix it.

📦 Today EXISTS

The catalog is a directory of pointers: name + runMode + runCommand + exePath + needs, reported by the client, kept in server RAM, gone on restart. Known-good entries in library.json are the only durable defs. One flat field set for every service, CLI and API alike.

🧰 Needed REQUIRED

A service is a container: a manifest + assets + templates + hooks. It carries its own install, verify, and upgrade logic. Its fields are structured per kind — a flag tree for CLIs, a template with exposed/hidden fields for APIs. It has a version and a history of failures it survived.

The container

Anatomy of a service container

One folder (or a .hydra zip) is the whole service — installed by dropping it in, like a ComfyUI custom node. The manifest is the docker-compose of services: the only file an agent or human needs to read to know everything about how to run it.

svc-sd/ # the container root (or svc-sd.hydra zip) ├── hydra.yaml # THE manifest — everything below is optional ├── assets/ # bundled files: scripts, icons, sample media ├── templates/ # API templates (ComfyUI-style workflows, JSON) ├── hooks/ # lifecycle: install.sh · verify.sh · upgrade.sh · on-fail.sh └── README.md # prose for humans, contracts for agents

Layer A — fields every service shares (global)

fieldmeaning
identityname · version · kind (cli | api | batch | stream) · source
ownershipauthor (clientId or hermes) · visibility (local | network | listed) · permissions
runtimerunMode · command | endpoint · needs (cores/gpu/ramMb/disk) · healthCheck
lifecyclehooks: install · verify · upgrade · on-fail
provenancecreatedBy · createdAt · improvedBy[] · history[] — the failure→fix chain, versioned

Layer B — fields per service kind (the tree)

CLI services get a flag tree (sd.exe has a hundred flags — group them, expose a few). API services get templates with an exposed/hidden split (ComfyUI's workflow JSON: the client sees five fields, never the node graph).

Reference example 1

sd.exe — the CLI flag tree

Stable Diffusion cpp is a prompt-flag machine: --prompt --cfg-scale --steps --sampler --control-net …. The container groups the tree and marks what a client may touch vs. what stays advanced.

# svc-sd/hydra.yaml
kind: cli
version: 1.4.2
command: sd.exe
needs: { cores: 8, ramMb: 16384, gpu: true }
fields:
  prompt:
    text:      { exposed: true, type: string,  help: "what to draw" }
    negative: { exposed: true, type: string,  help: "what NOT to draw" }
  sampling:
    steps:   { exposed: true,  type: int,    default: 20 }
    cfg:     { exposed: true,  type: number, default: 7.0 }
    seed:    { exposed: true,  type: int,    default: -1 }
    sampler: { exposed: false, type: select, options: [euler,ddim,dpmpp_2m] }
  model:
    checkpoint: { exposed: true, type: select, from: "assets/models/" }
    vae:       { exposed: false }
  video:                     # the long tail of flags — hidden, agent-tunable
    frames: { exposed: false }  fps: { exposed: false }  ...

The renderer (or MCP tool) renders only exposed fields as a form. Everything else is agent-tunable — the network's Hermes may adjust hidden flags when a run fails, and record why.

Reference example 2

ComfyUI — API template with exposed fields

ComfyUI is API-based and template-driven. The container bundles the workflow JSON as a template; the client sees a handful of knobs, the node graph stays inside.

# svc-comfy/hydra.yaml
kind: api
version: 2.0.1
endpoint: http://127.0.0.1:8188/prompt
healthCheck: GET /system_stats
templates:
  txt2img:  templates/txt2img.workflow.json   # {{prompt}} {{width}} {{height}} {{seed}}
  img2img:  templates/img2img.workflow.json
  upscale:  templates/upscale.workflow.json
exposed: [ prompt, width, height, seed ]   # the ONLY fields a client may set
hidden:  [ workflow graph, node internals, custom nodes ]

Install = drop the folder into ComfyUI's custom-node store, exactly like the ecosystem already does — the container spec simply standardizes what ComfyUI custom nodes already are, and extends it to every other kind of code.

The module rule

Composition — one format, any size

Break services into smaller modules where it makes logical sense. A container is never forced to be monolithic: a primitive wraps one executable or endpoint; a composite is a pipeline whose steps point at other containers. Same manifest format, recursively — a pipeline is just a container with a steps field.

svc-txt2img/ # a COMPOSITE container (a pipeline) ├── hydra.yaml │ kind: pipeline version: 3.0.0 │ steps: │ generate: { service: svc-sd@1.4, params: { prompt: "{{prompt}}", seed: "{{seed}}" } } │ upscale: { service: svc-upscale@0.9, params: { scale: 2 } } │ deliver: { service: svc-deliver@2.0 } │ flow: generate.output → upscale.input → deliver.input └── svc-upscale/ # a PRIMITIVE container, bundled as a dependency └── hydra.yaml # kind: cli · command: upscale.exe · needs: {cores:2, ramMb:4096}

🧩 Primitive

One exe or one endpoint. The leaf of the tree — sd.exe alone, a ComfyUI custom node alone. The unit the agent improves when a step fails.

🪜 Composite

Named steps with explicit data flow. One reqId per pipeline run, one verdict per step — the improvement loop is scoped: when upscale fails, the agent patches svc-upscale, never the whole pipeline.

ComfyUI is the living proof. A workflow is already a graph of small custom nodes — the container spec simply standardizes that pattern and extends it to every kind of code. And every module keeps the Hydra module standard: own directory · .d.ts contract · test() self-check — so the catalog can verify a module before trusting it.
The loop

Lifecycle — created by Hermes, improved by failure

Containers are authored by the network's Hermes (the agent attached to Hydra — a requirement, not an option). The supervised-install pipeline already writes blueprints and verdicts; this formalizes its output.

1Agent installsHermes installs code on a node → the output IS a container v1.0
→
2Catalogedmanifest → registry entry; visible per permissions
→
3Runsscheduler gates, runner executes, broker relays — unchanged
→
4Failsexit code, verdict taxonomy, health check, user report
→
5Agent improvespatches flags/hooks/template → v1.1 with history entry
The improvement chain is the memory. history[] records every failure→fix pair: v1.0 "OOM at 1024²" → v1.1 needs.ramMb 16384 · v1.1 "black images" → v1.2 cfg default 7.0. A container is a service that remembers how it learned to work — on this machine, and on the next one that installs it.
Who may do what

Permissions — created by client, server, or other client

Creation is not server-only. Any node can author or install a container — the owner client's policy decides what lands and who may use it.

actionwho maychecked where
author a containerthe node's Hermes · local user · (server with permission)client policy
install on a nodelocal user always · server / other clients only if allowedowner client policy (install permission)
run locallyany permitted requester — local UI or MCPexisting scheduler gate
run remotelyany permitted requester → broker → ownerbroker + owner's run policy
see fieldsexposed only · hidden = agent/ownermanifest Layer B
improvethe network's Hermes · ownerversioned history, never silent

Distribution mirrors the ecosystem Hydra already trusts: drop the folder, it appears — locally via the container store, network-wide via catalog sync (the registry grows from "reported state" to "replicated directory").

Bridge

What stays, what changes

✅ Stays

registry (catalog) · broker (routing) · scheduler (gate) · runner · MCP tools · reqId protocol · the event bus. The runtime path is untouched — containers feed it better inputs.

🔁 Changes

registry row → manifest-derived, versioned · known-good list → container store · defs get the two-layer field tree · library.json → seed of the store, not the whole story.

🌱 Grows

install permission UI · template rendering (exposed→form) · failure→fix history view · catalog replication · payment hooks on top of the same reqId plumbing.

Roadmap

From draft to door

  • v0.2 — manifest & authoring

    hydra.yaml schema lands; the supervised-install orchestrator emits a container as its success artifact; registry reads defs from manifests (versioned).

  • v0.5 — the two reference containers

    sd.exe ships as the CLI flag-tree reference; ComfyUI ships as the API-template reference. Renderer shows exposed-only forms. First composite pipeline (sd → upscale) proves the module rule. First failure→fix history entries recorded live.

  • v1.0 — the store & the loop

    Container store (custom-node-style install UX), permissions UI, catalog replication across nodes, and the improvement loop running unattended: fail → patch → version → re-serve.

North star: a service container is the unit of value in the marketplace — a verified, self-describing, self-improving piece of capability that any node can host. The marketplace doesn't sell access to machines; it trades containers.
