The Hydra MCP Server

The agent runtime's hands on the network — eleven typed tools that turn any MCP host (Hermes) into a driver of every client machine. One server. One endpoint. Per-session instances under the hood.

The short answer

Is there just one?

Asked plainly: yes — one MCP server, living in the Hydra server module server/src/modules/mcp/. It is served at a single endpoint, /mcp on the operator's port 8111. There is no MCP server on the clients — a client is a worker, not a host; its only local door is the tiny testapi (8123), which is an event trigger, not MCP.

One definition, per-session instances.

The module exposes one createServer() factory (server name hydra). Streamable HTTP means each connecting host gets its own session instance (a transport keyed by session id, swept after 5 minutes idle) — so many hosts can pair simultaneously without state bleeding between them. But every session runs the same eleven tools, wired to the same modules. It is one server wearing many session hats.

Architecture

Where it sits in the network

MCP HOST (Hermes agent) — paired: hermes mcp add hydra │ streamable HTTP (session id per host) ▼ /mcp · server :8111 · createServer() → 11 tools │ ├── clients.list ──────▶ clients module (registry: MAC identity, resources) ├── client.exec ───────▶ commands module (dispatch → WS → any client's shell) ├── client.kill ───────▶ commands module (process-tree kill via taskkill /T /F) ├── client.resources ──▶ clients module (waits for a FRESH manifest over WS) ├── client.review ─────▶ review module (deny-safe: THE one agent judges first) ├── sessions.get/wait ─▶ sessions module (streamed output, exit codes, replay) └── services.* ────────▶ services module (registry + broker: request/status/cancel) │ ▼ relays service.run / output / done over WS THE ONE AGENT (settings.json → 123:8642) ← review + chat only

Everything below the tools is the same machinery the operator console and the API use — the MCP server is a skin over modules, never a parallel implementation.

The tools

All eleven, exactly as registered

Each tool is a typed contract (zod input schema, description) — an agent reads the schema and knows precisely what to send.

toolwhat it doesshape
clients.listEvery connected client: identity, version, IP, online status, fresh resource manifest (CPU/RAM/GPU/disk).() → snapshot
client.execRun a shell command on any client (powershell or cmd). Returns a session id — output streams to sessions.get.(clientId, command, shell?)
client.killTerminate a running command on a client — process tree (taskkill /T /F).(clientId, sessionId)
client.resourcesAsk a client for a fresh manifest — never a cached boot snapshot. The gate's source of truth.(clientId)
client.reviewHermes reviews a command line by line before it runs. Deny-safe: any failure = no approval.(clientId, command, intent?)
sessions.getOne session: command, streamed stdout/stderr, exit code, duration. History replays.(sessionId)
sessions.waitPoll a session until it finishes (or timeout). The polite way to wait for a door command.(sessionId, timeoutMs?)
services.listEvery service on every client with live status (idle/queued/running/ok/error) + pending request count.() → clients[]
services.requestAsk ANY client to run a service owned by another client — the broker relays it. Params fill {{field}} in the owner's command.(name, owner, params?)
services.statusPoll one request: human step detail, buffered output (last 100 lines), verdict once done.(reqId)
services.cancelKill a remote job — relayed to the owner, process tree terminated.(reqId)
Capabilities

What it can do

🚪 The door CAN

Drive any client machine like SSH — no SSH, no RDP, no credentials. Running the client app IS opening the door. Verified live: the entire 123 box was driven through this door (found hermes, enabled api_server, killed a broken discord platform, LAN-bound 8642, launched the gateway).

🛡️ Review-first guardrail CAN

client.review routes a command to the ONE configured agent for line-by-line judgement before execution. Any failure, timeout, or malformed verdict = no approval. A live test rejected Remove-Item System32.

📦 Services end-to-end CAN

Human → Agent → GPU Worker → Verified Result: request a service on any node, watch human-step status, streamed output, and the verdict. Echo, Vision, LLMServer, and now sd-cli (Krea-2-Turbo image generation) ride this path.

📊 Fresh truth CAN

Resources are never cached across boot — client.resources forces a fresh collect, so the scheduler gate can never starve on a stale manifest. Sessions are replayable history, not fire-and-forget.

🔁 Kill on demand CAN

client.kill terminates the whole process tree of a runaway command; services.cancel does the same for a remote job. The operator never waits for a hang to time out.

🧩 Self-describing CAN

Every tool ships a description + input schema — any MCP-capable agent discovers the surface by reading it, no documentation ritual needed. The MCP host pairs once: hermes mcp add hydra.

Limits

What it can't do

Honest boundaries — some are design choices, some are on the roadmap, some are waiting for a decision.

can'twhy / status
Transfer filesNo file-download channel exists. The only push is the update exe swap. Proposed: one-time token + HTTP pull + hash verify — pending.
Register servicesServices enter via the client's known-good settings (edited at the machine or through the door) — there is no services.register tool yet.
Authenticate callersNo auth on /mcp. Running the server + LAN reachability = trust. A token slot is reserved for later.
Push events to the hostMCP is request/response. Live events relay over the internal WS (UI/requester paths); an MCP host must poll sessions/services.status.
Think with more than one agentReview and chat go to exactly ONE agent (settings.json → 123:8642). No fallback ladder by design.
Pay or rank anyoneNo reputation/payment — reqId + requester identity ride every request as the seed, but settlement is latent.
Directly control GPUs/modelsNo hardware tool — that's what services are for (LLMServer wraps llama.cpp). The MCP server orchestrates; it doesn't micromanage.
Survive a server crash mid-requestPending/recent state is in-memory; a server restart forgets in-flight jobs (the JSONL log remembers what happened, not what was pending).
Reaching it

Three ways in

# 1 — the pair (Hermes as host, the intended path)
hermes mcp add hydra --url http://<server>:8111/mcp

# 2 — the back door (raw MCP client from the shell)
node scripts/mcp-call.cjs clients.list
node scripts/mcp-call.cjs services.request '{"name":"sd-cli","owner":"hydra-2a466f0439c8","params":{"prompt":"a red apple"}}'

# 3 — the native wrapper (Hermes tools, as this agent uses them)
mcp__hydra__clients_list · client_exec · sessions_wait · services_request · ...

# endpoint facts
URL     http://192.168.1.100:8111/mcp   (streamable HTTP; session id per host)
SERVER  name 'hydra' · version = config.version
SESSIONS transport map, 5-minute idle sweep · multiple hosts can pair at once
Trust model

Why it's safe enough

The door is the consent. Running the client app = opening the door; the server never forces a door open. The review channel is the tripwire for anything dangerous. Clients survive server crashes (backoff reconnect). The MCP surface is typed, so an agent can't invent a tool — it can only use the eleven. The riskiest thing in the network is a hostile MCP host reaching an open door — mitigated today by LAN trust, tomorrow by the reserved token slot.
